## 1. 문서 목적과 기준

- `v1.9.3`의 Phase 0 본문, 부록 1·4·5·9, 제III편 D절에서 요구사항을 추출한다.
- `v1.9.3` 전체를 반복해서 읽지 않고, 수식·계약·오픈소스 조항 확인이 필요한 경우에만 해당 구간을 참조한다.
- 각 요구사항을 설계(`D*`), 시험(`D7`·`D10`·`D11`), 구현, 결과(`I2`·`T1`·`T2`·`T7`)에 추적한다.
- `R1.md`와 `D12.md`는 생성하지 않는다. `v1.9.3`은 상위 요구사항 기준서로 직접 참조하고, MNIST 분할·초기데이터 설계는 `D4.md`/`D5.md`에 통합한다.

### 상태 표기

| 상태 | 의미 |
| :--- | :--- |
| `소급 PASS` | 기존 구현과 실행 증거를 바탕으로 문서화한 상태. 이번 `R3.md` 작성에서 구현·테스트를 다시 실행하지 않음 |
| `설계 전` | 요구사항은 확정됐지만 설계·구현·시험 결과는 아직 없음 |
| `미검증` | 구현 또는 문서는 있으나 PASS를 뒷받침할 실행 증거가 부족함 |

- 기존 전체 회귀 **408 passed**와 CLI 검증 증거는 `STATE.md` 및 기존 결과서를 근거로 사용한다.
- 독립 auditor 감사는 공급자 제한으로 미완료 상태다. 따라서 `소급 PASS`는 독립 감사 완료를 의미하지 않는다.

## 6. 요구사항 변경 관리

- 구현 난이도만으로 요구사항이나 수용 기준을 바꾸지 않는다.
- 기술적 한계·명백한 오류·요구사항 충돌이 확인되면 다음 항목을 먼저 보고한다.
  - 문제 요구사항 ID와 원문 출처
  - 재현 증거 또는 기술적 근거
  - 대안과 장단점
  - 설계·시험·일정·다른 요구사항에 미치는 영향
  - 승인 여부
- 승인된 변경만 `R3.md`와 관련 `D*` 문서에 반영하고, 이전 수용 기준은 변경 이력에 남긴다.
